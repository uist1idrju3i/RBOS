# 文書の構造と分割

## 基本方針

- `docs/` は GitHub Pages で公開するサイト専用です。内部文書は `docs/` に置きません。
- 目的と読者で分けます。利用者向けの公開サイト、開発者向けの手順、調査の記録は別の文書です。
- 分割した文書から親の索引へ戻れるようにし、索引にない孤立した文書を作りません。
- 本文と根拠を二重にコピーしません。要約とリンクにします。
- 現在の決定と、取りやめた計画・当時の仮説を区別します。過去の本文は後の知識で改変せず、冒頭から現在の決定へ案内します。

## 禁止する分け方

- 行数・バイト数だけを見た機械的な切断。
- 見出し、表、コードブロックの途中での切断。
- 必須の条件、否定条件、例外、失敗した試行を別ページへ追い出す分割。
- 閾値回避だけを目的にした細片化。

## 整理の前に決めること

入力は対象文書、基準の commit、依頼の範囲、リンク検査の結果です。公開サイト、開発手順、調査記録、履歴・出典に分類し、各主題の本文をどこに置くかを決めます。

- 重複候補は代表文に加え、数値、条件、否定、出典、失敗例まで照合します。違いを判断できない場合は削除を止め、相違点を記録します。
- 原文の引用と実験の生データは、文章の整理のためには変更しません。誤りの訂正は元の値・理由・訂正後の根拠を残します。
- 公開サイトに内部向けの調査メモや未確認事項を混ぜません。公開してよい内容だけを `docs/` に置きます。

## 分割の判断順序

1. 棚卸し: `git ls-files '*.md' '*.html'` と対象ディレクトリで、文書と公開サイトの境界を把握します。
2. 意味単位の選定: 各節が「読者と目的」「主題」「手順」「証拠」「参照情報」のどれとして独立して答えられるかを判断します。
3. 既存の主題文書との照合: 移動先が既に同じ主題を扱っていないか、代表文で確認します。内容が既に収録されているなら移動せず、要約とリンクに置き換えます。
4. 移動: `git mv` または節の抽出で移し、内部の参照先を直します。数値、条件、出典、失敗記録は本文の移動先に保ちます。
5. 照合: 移動の前後で、見出し、内部リンク、他文書からの参照、条件、失敗記録、ライセンス・出典が失われていないことを確かめます。

## 提出前の確認

- [ ] `docs/` に公開サイト以外のファイルを置いていない
- [ ] 各主題の本文の置き場が明確で、親索引と戻り先がある
- [ ] 旧見出し・条件・出典・失敗記録を移動前後で照合した
- [ ] 現在の決定と過去の計画を読み分けられる
- [ ] リンク切れと個人環境のパスがないことを確認した
